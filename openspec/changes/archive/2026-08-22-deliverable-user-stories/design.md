## Context

`Deliverable` (backend/src/prisma/schema.prisma:97-104) is a flat model (`id`, `name`, `description`, timestamps) with no child resources. `Form` (schema.prisma:47-60) is already the app's structured-data primitive: it's created from a `FormTemplate` (`formTemplateId`, required at creation), clones that template's `FormTemplateField`s into its own `FormField`s at creation time, and holds at most one `FormResponse` (`response_data` JSON, filled/edited via `PUT /api/v1/forms/:formId/response`, see `openspec/specs/form-responses/spec.md`). A user story is meant to be exactly this kind of structured record, not free text — so a `UserStory` is modeled as an extension of `Form`, and an `AcceptanceCriterion` as an extension of `UserStory`'s sibling concept, also extending `Form`.

The codebase's one existing nested-list pattern is `FormTemplate` → `FormTemplateField`: per-item CRUD plus a `PUT .../order` endpoint that rewrites `order_index` for the full set in one transaction (`backend/src/modules/form-templates/`, `openspec/specs/form-templates/spec.md`).

## Goals / Non-Goals

**Goals:**
- A `UserStory` and an `AcceptanceCriterion` both hold structured, template-defined data — created by picking a `FormTemplate`, exactly like creating a `Form`.
- Reuse `Form`'s existing fill-in-answers endpoint (`PUT /forms/:formId/response`) unchanged for both user stories and acceptance criteria, and its edit endpoint (`PATCH /forms/:formId`) for a user story's `name`/`description`, since they *are* forms.
- Any existing `FormTemplate` can be used to create a user story or an acceptance criterion (no template categorization).
- An `AcceptanceCriterion` has no `name`/`description` of its own — it is identified solely by its source `FormTemplate` and its structured answers.

**Non-Goals:**
- No restriction on which `FormTemplate`s are eligible for user stories vs. acceptance criteria vs. plain forms.
- No changes to `Form`'s own schema or its plain CRUD behavior beyond the new cascading-delete side effect (below).
- No third nesting level below `AcceptanceCriterion`.
- No editing of an acceptance criterion's `name`/`description` — there is nothing to edit.

## Decisions

- **`UserStory` and `AcceptanceCriterion` extend `Form` via a shared primary key** ("table-per-type" inheritance — Prisma has no native inheritance, so this is the standard relational approximation): `UserStory.id` is both its own primary key and a foreign key to `Form.id` (`onDelete: Cascade`); `AcceptanceCriterion.id` works the same way. `UserStory` additionally carries `deliverableId` (FK → `Deliverable`, `onDelete: Cascade`) and `order_index`; `AcceptanceCriterion` carries `userStoryId` (FK → `UserStory`, `onDelete: Cascade`) and `order_index`. Neither table duplicates `name`, `description`, or timestamps — those live only on the underlying `Form` row.
  - Alternative considered: a `formId` foreign key on separate `UserStory`/`AcceptanceCriterion` tables (wrapper-references-Form) instead of sharing the primary key. Rejected per explicit direction to model this as inheritance/extension of `Form`, not a reference to one.
  - Alternative considered: add `deliverableId`/`userStoryId` directly onto `Form`. Rejected — it would make every `Form` carry columns only meaningful for the subset used as user stories/acceptance criteria, and conflates the general-purpose `Form` concept with this feature.
- **Creating a `UserStory` or `AcceptanceCriterion` composes `Form`'s creation logic into one transaction.** The existing `FormsService.createForm` clones the target `FormTemplate`'s fields into new `FormField` rows in a transaction scoped to that call alone; it cannot be reused as-is because creating a `UserStory` needs the *same* transaction to also insert the `UserStory` row (same id as the new `Form`) — doing it as a second, separate call would risk an orphaned `Form` if the second insert failed. `FormsService` will be refactored to expose the field-cloning step as a reusable set of Prisma operations (e.g. a `buildCreateFormOperations(id, dto)` helper) that both `createForm` and the new user-story/acceptance-criterion creation logic compose into their own `$transaction`.
- **Deleting a user story or acceptance criterion is implemented as deleting its underlying `Form`.** Because the FK direction is subtype → base (`UserStory.id → Form.id`), Postgres cascade only flows *from* deleting the `Form` *to* removing the `UserStory`/`AcceptanceCriterion` row — never the reverse. So `DELETE /deliverables/:deliverableId/user-stories/:userStoryId` and `DELETE /user-stories/:userStoryId/acceptance-criteria/:acceptanceCriterionId` delete the `Form` row with that id, relying on cascade to remove the wrapper row (and, transitively, that acceptance criterion's own row if deleting one).
- **Deleting a `UserStory` or a `Deliverable` must explicitly clean up descendant `Form`s bottom-up**, since a `Deliverable`/`UserStory` row's own cascade (via `deliverableId`/`userStoryId`) only removes wrapper rows, not the `Form`s underneath them, which would otherwise be orphaned:
  - Deleting a `UserStory`: in one transaction, delete the `Form`s backing all of its `AcceptanceCriterion`s, then delete the `Form` backing the user story itself.
  - Deleting a `Deliverable`: in one transaction, delete the `Form`s backing every `AcceptanceCriterion` of every `UserStory` on it, then the `Form`s backing those `UserStory`s, then the `Deliverable` row.
- **New `UserStoriesModule`** hosts two controllers — one for `/deliverables/:deliverableId/user-stories` (create/delete/reorder), one for `/user-stories/:userStoryId/acceptance-criteria` (create/delete/reorder) — rather than folding this into `DeliverablesModule`, since the logic spans `Deliverable`, `Form`, and `FormTemplate` and doesn't belong to any single existing module. It depends on `FormsModule`/`PrismaService` for the shared creation/deletion helpers.
- **`GET` responses embed the full tree.** `GET /api/v1/deliverables` and `/deliverables/:deliverableId` include `userStories` (sorted by `order_index`), each shaped like a `Form` response (name, description, template info, fields, response) plus `order_index` and its own `acceptanceCriteria` array — the same shape *minus* `name`/`description`, sorted by `order_index`. No separate `GET /user-stories/:userStoryId` endpoint is added; `GET /forms/:formId` already returns the same underlying data by id if a direct fetch is needed.
- **Editing content and filling answers reuse `Form`'s existing endpoints unchanged** (`PATCH /forms/:formId`, `PUT /forms/:formId/response`) — no new edit/fill endpoints for user stories or acceptance criteria.
- **An `AcceptanceCriterion` has no `name`/`description`, but its underlying `Form` row still needs a `name`** (`NOT NULL` in the schema, unchanged for this feature). `CreateAcceptanceCriterionDto` accepts only `formTemplateId`; `FormsService.buildCreateFormOperations` falls back to the source `FormTemplate`'s name when the caller supplies none, so the invariant holds without touching `Form`'s schema. `AcceptanceCriterionResponseDto` and `AcceptanceCriteriaService.toAcceptanceCriterionResponse` explicitly omit `name`/`description` from what's exposed, even though the row backing it has them internally.
  - Alternative considered: make `Form.name` nullable so `AcceptanceCriterion` can leave it unset. Rejected — it would ripple into the general `forms` capability (list/edit pages, `CreateFormDto` validation) for a need specific to this one subtype.

## Risks / Trade-offs

- [Orphaned `Form` rows if deletion order is implemented incorrectly] → The bottom-up explicit-delete rule above is the one place this feature deviates from "let the database cascade handle it"; it must be applied consistently in both the user-story delete path and the deliverable delete path. Covered by the e2e tests in tasks.md (deleting a deliverable/user story leaves no orphaned forms).
- [Extending `FormsService` to expose reusable creation internals slightly increases its surface area] → Scoped to a single new internal helper method rather than duplicating the field-cloning logic in the new module.
- [A `UserStory`/`AcceptanceCriterion` is indistinguishable from a plain `Form` at the `/forms` endpoints — e.g. `GET /api/v1/forms` would list them too] → Accepted: they genuinely are forms, and this MVP extension doesn't need to hide or filter them out of the general forms listing. Can be revisited if that proves confusing in practice.
